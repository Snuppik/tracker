# 04. REST API — контракт

Машинно-читаемая версия: **`api/openapi.yaml`** (она первична, этот документ — пояснение к ней).
Бейс: `http://localhost:8080`. Все эндпоинты — `/api/*`, JSON, UTF-8.

## 1. Соглашения

| Параметр | Соглашение |
|---|---|
| Версионирование | Отсутствует (`/api/v1` не добавляем — 4 дня, одна версия) |
| Имена полей | `snake_case` во всех телах запросов и ответов |
| Время | Только RFC3339 с зоной: `2026-10-29T15:30:00Z`. Сервер наружу отдаёт **UTC**, принимает с любым смещением |
| ID | Строка UUID v7. В URL — `/api/tasks/{id}`; невалидный UUID → `400`, а не `500` |
| Контент | `Content-Type: application/json; charset=utf-8`. Форма не поддерживается |
| Авторизация | Cookie `tracker_session` (JWT). Заголовок `Authorization` не используется |
| `PATCH` | Частичное обновление: обновляются только присутствующие в теле ключи |
| Кэширование | Все ответы `/api/*` — `Cache-Control: no-store` |
| Пагинация | `limit` (по умолчанию 50, максимум 200), `offset` (по умолчанию 0). В ответе — `total` |
| CORS | Не нужен: фронт раздаёт тот же origin (`00-decisions.md` T-11). Не добавлять |

### Формат ошибки — единственный на весь API

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Проверьте правильность заполнения полей",
    "details": [
      { "field": "title", "message": "обязательное поле" },
      { "field": "due_at", "message": "неверный формат, ожидается RFC3339" }
    ]
  }
}
```

| HTTP | `error.code` | Когда |
|---|---|---|
| 400 | `validation_failed` | Невалидное тело/query/ID. `details` обязателен |
| 401 | `unauthorized` | Нет cookie / битый / просроченный JWT. Также — неверный email или пароль при входе (чтобы не различать «нет пользователя» и «неверный пароль») |
| 403 | `forbidden` | Право есть, доступ запрещён (в MVP не используется: чужая задача отдаётся 404) |
| 404 | `not_found` | Ресурс не существует **или принадлежит другому пользователю** |
| 409 | `conflict` | Email уже зарегистрирован; дубликат push-подписки |
| 422 | `limit_exceeded` | Превышен лимит (например, >5 напоминаний на задачу) |
| 500 | `internal` | Неизвестная ошибка. Текст — обезличенный, подробности только в лог |

Правило маппинга: `service` возвращает доменные ошибки (`model.ErrNotFound`, `model.ErrConflict`, `model.ErrValidation{...}`, `model.ErrLimitExceeded`), **единственный** `httpapi/errors.go` превращает их в коды. В хендлерах — никаких `http.Status...` за пределами `response.go`/`errors.go`.

## 2. Авторизация

| Метод | Путь | Auth | Тело | Ответ |
|---|---|---|---|---|
| POST | `/api/auth/register` | — | `{email, password, name}` | `201` + `{user}` + cookie |
| POST | `/api/auth/login` | — | `{email, password}` | `200` + `{user}` + cookie |
| POST | `/api/auth/logout` | ✔ | — | `204`, cookie сброшен |
| GET | `/api/auth/me` | ✔ | — | `200` + `{user}` |

`{user}` = `{ "id", "email", "name", "created_at" }`. Пароль никогда не возвращается.

Валидация регистрации: `email` — упрощённая проверка `^.+@.+\..+$` + не более 254 символов, нормализуется в `lower()`; `password` — 8…72 байта; `name` — 1…100 символов.

## 3. Задачи

| Метод | Путь | Auth | Назначение |
|---|---|---|---|
| GET | `/api/tasks` | ✔ | Список с фильтрами |
| POST | `/api/tasks` | ✔ | Создать |
| GET | `/api/tasks/{id}` | ✔ | Деталь (включая напоминания) |
| PATCH | `/api/tasks/{id}` | ✔ | Частичное обновление |
| PUT | `/api/tasks/{id}/status` | ✔ | Смена статуса (drag&drop) |
| DELETE | `/api/tasks/{id}` | ✔ | Удалить |

**Query для `GET /api/tasks`:** `status`, `priority`, `search`, `sort` (`due_at|created_at|priority`, по умолчанию `due_at`), `dir` (`asc|desc`, по умолчанию `asc`), `limit`, `offset`.
Нераспознанное значение фильтра → `400 validation_failed` (а не «молча игнорируем» — иначе фронт будет час искать, почему фильтр «не работает»).

**Тело `POST /api/tasks`** (`PATCH` — тот же набор, все поля опциональны, кроме пустого тела):

```json
{
  "title": "Сдать отчёт",
  "description": "Проверить цифры за октябрь",
  "priority": "high",
  "due_at": "2026-10-29T15:30:00Z"
}
```
`status` в `POST` принимается, но по умолчанию `todo`; смена статуса — только через `/status` (единая точка для бизнес-правила «при done отменяем напоминания»).

**Объект задачи в ответах:**

```json
{
  "id": "0198a3f1-7c2d-7xxx-xxxx-xxxxxxxxxxxx",
  "title": "Сдать отчёт",
  "description": "Проверить цифры за октябрь",
  "status": "in_progress",
  "priority": "high",
  "due_at": "2026-10-29T15:30:00Z",
  "overdue": false,
  "due_soon": true,
  "reminder_count": 2,
  "created_at": "2026-10-26T18:00:00Z",
  "updated_at": "2026-10-26T19:10:00Z"
}
```

`overdue` и `due_soon` считает сервер (`due_at < now` и `now ≤ due_at < now+24h`, оба только при `status != 'done'`). Причина: этот же критерий используют `insights` и дашборд — три места с разным определением «горящей» задачи гарантированно разбегутся. Фронт их не пересчитывает.

**Список:**

```json
{ "items": [ /* task */ ], "total": 37, "limit": 50, "offset": 0 }
```

**`PUT /api/tasks/{id}/status`** → `{ "status": "done" }` → `200` с обновлённым объектом задачи.
Побочный эффект (важно!): при переходе в `done` все `pending`-напоминания задачи переходят в `expired` в той же транзакции. Выполненную задачу напоминать не нужно.

**`GET /api/tasks/{id}`** возвращает задачу плюс вложенный массив `reminders` (см. §4) — один запрос вместо двух на открытии модалки.

## 4. Напоминания

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| GET | `/api/tasks/{id}/reminders` | — | `{items:[reminder]}` |
| POST | `/api/tasks/{id}/reminders` | `{fire_at, message}` | `201` + reminder |
| DELETE | `/api/reminders/{id}` | — | `204` |

```json
{
  "id": "0198a3f2-...",
  "task_id": "0198a3f1-...",
  "fire_at": "2026-10-29T15:25:00Z",
  "message": "За час до дедлайна",
  "status": "pending",
  "created_at": "2026-10-26T19:00:00Z"
}
```

Правила (все — в `service/reminders.go`, не в хендлере):
- `fire_at` строго в будущем, допуск на часы браузера: не раньше `now - 60s`. Иначе пользователь «успевает» создать напоминание в прошлом, и оно сработает на следующем тике — это выглядит как баг.
- `now + 5 лет` — верхняя граница.
- не более **5** активных (`pending`) напоминаний на задачу → `422 limit_exceeded`.
- задача должна принадлежать пользователю → иначе `404`.
- `DELETE` по чужому `id` → `404` (запрос всё равно скоупится `WHERE id=$1 AND user_id=$2`).
- `status` напоминания меняет только планировщик; клиент его не пишет.

## 6. Уведомления (in-app лента)

| Метод | Путь | Ответ/Тело |
|---|---|---|
| GET | `/api/notifications?unread=true&limit=50` | `{items:[notification], unread: 3}` |
| POST | `/api/notifications/{id}/read` | `204` |
| POST | `/api/notifications/read-all` | `204` |

```json
{ "id": "0198a3f5-...", "task_id": "0198a3f1-...", "kind": "reminder",
  "title": "Сдать отчёт", "body": "За час до дедлайна", "read": false,
  "created_at": "2026-10-29T15:25:01Z" }
```

`unread` в ответе всегда считается полным количеством непрочитанных (не только в текущей странице) — иначе бейдж врёт при >50 уведомлениях.

## 7. Web Push

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| GET | `/api/push/public-key` | — | `200` `{"public_key": "<VAPID public, base64url>"}` |
| PUT | `/api/push/subscription` | `{endpoint, keys:{p256dh, auth}}` (сырой `PushSubscription.toJSON()`) | `201` |
| DELETE | `/api/push/subscription` | `{endpoint}` | `204` |

`PUT` идемпотентен: существующий `endpoint` → обновляем `last_seen_at/p256dh/auth`, `201`. Фронт вызывает его при каждой загрузке приложения, если есть активная подписка — этого достаточно, чтобы подписка не протухала (endpoint и ключи меняются у браузера не предсказуемо).

## 8. Служебные

| Метод | Путь | Auth | Назначение |
|---|---|---|---|
| GET | `/healthz` | — | `200 {"status":"ok"}` — процесс жив (для `wget`/демо) |
| GET | `/readyz` | — | `200`/`503` — `SELECT 1` к БД (healthcheck в compose) |
| GET | `/`, `/login`, `/css/*`, `/js/*`, `/sw.js` | — | Статика. Всё, что не `/api/*`, `/*.{css,js,html,...}` и не служебное → `index.html` |

`/sw.js` обязан отдаваться с `Content-Type: text/javascript` и **без** `Cache-Control: immutable` (иначе обновление Service Worker затянется).

## 9. Что сознательно НЕ делаем

Rate limiting на login, refresh-токены, отзыв отдельных сессий, `Authorization`-заголовок, API-ключи, вебхуки, `OPTIONS`/CORS, HATEOAS-ссылки, версионирование, пагинация курсором, батч-эндпоинты, `GET /api/tasks/{id}/status-history`.
Если очень хочется — см. «Запрещённый список» в `AGENTS.md` §7.
