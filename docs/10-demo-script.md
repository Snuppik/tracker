# 10. Сценарий хакатонного демо

## 1. Общая информация

| Параметр | Значение |
|---|---|
| Название | Tracker |
| Тип | Веб-приложение личного трекера задач |
| Стек | Go 1.27, PostgreSQL 16, vanilla HTML/CSS/JS, Web Push |
| Длительность | ≤ 4 минуты (питч) + 1 мин «запас» |
| Демо-машина | Ноутбук с `http://localhost:8080` (Chrome или Edge) |
| Хранение | Один репозиторий, `docker compose up -d` |
| Данные | Заполняются вживую (нет seed-скрипта — см. `00-decisions.md` P-7) |
| Запасной сценарий | Если push не работает (не localhost) — in-app лента, тот же эффект |

## 2. Сценарий (минута за минутой)

### Минута 1: «Проблема + запуск» (0:00 – 1:00)

**Текст спикера:**

> «Мы все теряем задачи: в переписке, в заметках, в голове. Дедлайн прошёл — а задача так и не начата.
> 
> Tracker — это веб-приложение, которое превращает хаос дел в упорядоченный список: задачи с приоритетом, дедлайнами и напоминаниями. И всё это работает в одном Docker-контейнере.
> 
> Вот как это выглядит после `docker compose up -d`...»

**Действие:**
1. Открываем терминал → `make demo` (или `docker compose down -v && docker compose up -d --build`)
2. Ждём ~40 секунд → в браузере `http://localhost:8080`
3. Показываем, что `tracker-postgres` и `tracker-api` поднялись

**Переход:**
> «Регистрация, вход — и мы на доске. Каждому — только свои задачи. Если залогиниться под другим аккаунтом, чужой список пуст — и даже по прямому URL задачу не увидеть.»

### Минута 2: «Ядро» (1:00 – 2:00)

**Действие:**
1. Создать 2–3 задачи с разными приоритетами и дедлайнами (включая одну просроченную, одну на завтра)
2. Перетащить карточку из `К работе` → `В работу` → `Готово`
3. Показать, что дашборд обновился (счётчики: «В работе 1», «Готово за неделю 1»)
4. Переключиться на список — показать фильтры и поиск
5. Показать, что просроченная задача подсвечена красным, а «горящая» — оранжевым

**Текст спикера:**

> «Доска kanban — три колонки, карточки с приоритетом и дедлайном. Перетаскивание мышью меняет статус в реальном времени: даже после перезагрузки страницы состояние сохраняется.
> 
> Список — для фильтрации и поиска. Просроченные задачи подсвечены красным, горящие (менее 24 часов до дедлайна) — оранжевым. Счётчики дашборда всегда сходятся с содержимым доски.»

### Минута 3: «Напоминания и пуш» (2:00 – 3:00)

**Действие:**
1. Открыть задачу → вкладка «Напоминания» → создать напоминание на `now + 30 сек`
2. Переключиться на вкладку браузера (или свернуть окно)
3. Через 30 секунд показать всплывающее системное уведомление (или запись в колокольчике, если push не сработал)
4. Показать, что в блоке «Аналитика» появилась подсказка

**Текст спикера:**

> «Напоминания — пользователь сам ставит таймер к любой задаче: «напомнить за час до дедлайна», «через 3 дня». Напоминание доставляется двумя способами: через in-app ленту (внутри приложения, работает всегда) и через Web Push (системное уведомление браузера — работает на localhost).
> 
> А ещё Tracker анализирует ваш список и говорит: «4 задачи горят сегодня» или «Задача в работе без дедлайна уже неделю». Это не нейросеть, которая «может ошибиться» — это детерминированные правила, результат всегда предсказуем.»

### Минута 3.5: «Архитектура» (3:00 – 3:30)

**Текст спикера (быстро, без слайдов):**

> «Бэкенд — Go 1.27, stdlib `ServeMux`, `database/sql` поверх pgx, PostgreSQL в контейнере. Внешних зависимостей — 5, включая Web Push. Фронтенд — vanilla HTML/CSS/JS, без сборщиков, без фреймворков. Статику отдаёт Go. Один контейнер, один порт, ноль CORS. Включается одной командой.
> 
> Тесты покрывают auth и CRUD. Linter и vet — зелёные. Форматирование — gofmt.»

### Минута 4: «Итоги» (3:30 – 4:00)

**Текст спикера:**

> «Tracker — это замкнутый цикл: задача → дедлайн → напоминание → пуш → аналитика.
> 
> Три человека, 4 дня, один Docker-контейнер.
> 
> Спасибо, готовы ответить на вопросы.»

## 3. Запасной сценарий (если что-то не работает)

| Что сломалось | Запасной вариант | Что говорить |
|---|---|---|
| Push не пришёл (не localhost) | Показать запись в in-app ленте | «Web Push — дополнительная доставка, работает на localhost/HTTPS. In-app лента — основная, работает всегда» |
| `docker compose up` не стартует | Показать `go run ./cmd/api` + `psql` | «Бэкенд локально, база локально. Docker — для переносимости на хакатоне» |
| Баг в DnD | Использовать select статуса на карточке | «DnD — основное взаимодействие, select — запасной путь для тач-устройств» |
| Insights не выдали подсказку | Создать тестовую задачу с дедлайном в прошлом | «Инсайты реагируют на конкретные паттерны — покажу на примере» |
| Нет интернета | Приложение работает полностью офлайн (нет внешних запросов) | «Tracker не требует интернета — все ресурсы локальны, работает в любом месте» |

## 4. Критерии приёмки финального MVP (проверяются по порядку)

1. ✅ `git clone` → `docker compose up -d --build` → `http://localhost:8080` = страница входа
2. ✅ Регистрация нового пользователя → авто-вход → пустая доска
3. ✅ Создание 5 задач с разными приоритетами и дедлайнами → все видны в `todo`
4. ✅ Перенос карточки `todo → in_progress` → F5 → карточка в `in_progress` (**главный тест**)
5. ✅ Переключение на список → фильтр «высокий приоритет» + поиск → счётчик сходится
6. ✅ Просроченная задача = красный, горящая = оранжевый
7. ✅ Напоминание → всплывающее уведомление (системное ИЛИ в колокольчике)
8. ✅ Блок «Аналитика» → осмысленная подсказка
9. ✅ Второй аккаунт → пустой список задач (даже по прямому URL)
10. ✅ `go test ./...` зелёные, `gofmt -l .` пуст, `go vet ./...` без замечаний

## 5. Распределение ролей на сцене

- **Спикер** (Backend): питч, запуск docker, объяснение архитектуры.
- **Демонстратор** (FE1): заполнение задач, drag&drop, напоминания, push.
- **Подстраховщик** (FE2): если демонстратору нужно — переключение на список, фильтры, дашборд, ответы на вопросы по фронтенду.

Перед хакатоном: **минимум 2 полных прогона вслух** с таймером (цель — 3:45, запас 15 секунд). Каждый прогон — полный, от `docker compose up` до финальной фразы.

## 6. Вопросы от жюри (подготовить ответы)

| Возможный вопрос | Краткий ответ |
|---|---|
| Почему не React/Vue? | 4 дня, один фронтендер, native API + vanilla JS быстрее и проще. React = билд-система + `node_modules` + время на изучение фреймворка. Здесь нет состояния, которое требует виртуального DOM |
| Почему не gRPC? | Браузер не поддерживает gRPC без прокси и кодогенерации. REST + JSON — нативный протокол браузера. Один HTTP-запрос, один `fetch` |
| Почему не ORM? | 15 SQL-запросов на весь проект. GORM — абстракция ради абстракции. `database/sql` с pgx — стандартная библиотека Postgres |
| Почему `text` вместо `enum` в Postgres? | `ALTER TYPE` ломает миграции. CHECK + `ALTER CONSTRAINT` работает в любом случае. Для MVP это проще |
| Что если 1000 задач? | Пагинация (limit 200 max), индексы по `user_id` + `status`/`due_at`. При 1000 задачах `ListTasks` — один индексный scan |
| Как обрабатываются ошибки валидации? | Сервер → `400` с `details: [{field, message}]` → фронт показывает под полем. Без дублирования правил |
| Push работает на телефоне? | На Chrome Android — да. На Safari iOS — только если PWA добавлен на домашний экран. На десктопе (Chrome/Edge) — да |
| Инсайты — это LLM? | Нет, детерминированные SQL-правила. Результат всегда предсказуем и воспроизводим |
| Почему не WebSocket? | Задержка 30 с допустима, polling проще и не требует heartbeat/переподключения |
| Как тестируется? | `httptest` на каждый хендлер (auth, CRUD, ошибки), `go vet`, `gofmt`, прогон сценария демо ≥ 2 раза |

## 7. Что НЕ делать на сцене

- Не показывать `docker compose` без пояснения (жюри не знает, что это).
- Не переходить к коду (кроме одного экрана с `go test ./...`).
- Не раскрывать детали реализации (bcrypt cost, pgx driver) без вопроса.
- Не задерживаться дольше 1 мин на каждом блоке.
- Не извиняться за баги — использовать запасной сценарий.
